# ShareX-Mod v0.4.4-dev

Focus: give every artifact produced by one scrolling capture an explicit shared session identity.

## Why this is needed

v0.4.2 introduced Capture Map / Quality Guard. v0.4.3 added Capture Boundary and Repair Plan. Those components currently create separate timestamped directories. Selecting "the newest" capture-map is acceptable for a prototype, but it is not safe enough for rapid consecutive captures or future concurrent/background work.

Local repair must never use evidence from the wrong capture.

## Unified Capture Session

At capture start, v0.4.4 creates one lightweight correlation context:

`ShareX-Mod/CaptureSessions/<session-id>/session-manifest.json`

Existing component output locations are preserved. Components register their real directories with the session manifest instead of being forcibly moved.

Registered components currently include:

- `quality`: Capture Map / Quality Guard directory
- `boundary`: Capture Boundary directory
- `segments`: smart-segmentation / final PNG directory
- `repair`: Repair Plan directory

The manifest stores the shared session ID, selected capture rectangle, result size, final status/end reason, and the registered component paths.

## Repair-plan safety

`ShareXModRepairPlanner` now first resolves the Capture Map through the active session context. The previous "find newest map from this process" behavior remains only as a compatibility fallback.

This removes the main ambiguity before v0.5 introduces browser semantic coordinates and exact regional re-capture.

## v0.5 handoff

The next browser-aware layer can register:

- `semantic-map`
- `layout-shifts`
- `browser-repair`
- `resource-evidence`

under the same session ID, allowing a damaged logical range to be traced back to the exact DOM/layout snapshot used for that capture.
